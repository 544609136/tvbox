二、去重是怎么做的（关键）

「重复」在点播源里有两层，两层都去了：
① URL 层：按 host + path 归一，把 ?ac=list、结尾 /、 大小写差异等同一条接口合并 —— 从 1783 条降到 1482 条唯一端点。
② 内容层：抓每个站前 20 个片名，做片单重叠率判断。 若一个新站 ≥70% 的片目已被保留站覆盖，说明是同一上游，丢弃。
成人标记站豁免去重：成人站不参与「被覆盖就丢」的判重，全部保留（含内容重复的）， 因为「是不是成人、要不要留」由你判断，不该被去重顺手砍掉。
为什么不用 md5(前 8 个标题)：前 8 条片名在 NATIVE 系源之间高度同质（新片都一样）， 8 条签名会把可播站误压到 37 站 —— 过度合并。20 条 + 重叠率阈值更稳。
③ 另剔除了 第三方反代包源（形如 xxx.eu.org/https://真后端/...） ——16 个上游挤在一个 host 上，单点一挂全灭，且多一跳延迟（成人站同样豁免，不剔除）。

点播源分两类，别混看：
· 真直链（147 个）：播放地址是 m3u8/mp4，不需要解析器，桌面端也能播。 实测吞吐最高的：爱奇艺资源 1955KB/s、暴风影视 596KB/s。
· 需解析器（15 个）：播放地址指向爱奇艺/芒果等网页播放页， 靠 parses 解析。手机/电视端可用，桌面端会挂，已单独分组标注。
本轮修正的一个测速假象：旧方法只判断「能不能拉到字节」， 把爱奇艺网页 HTML 当分片算，测出假的 646KB/s。现在必须先确认 「拉到的是 m3u8 索引或 ftyp」，再算吞吐 —— 这类源的真实身份是「需解析器」。
排序：数组顺序 = TVBox 界面顺序 —— 点播放最前（162 站：147 个真直链按吞吐降序 + 15 个需解析器）， 后面才是特殊功能（网盘分享 → 网盘搜索 → 磁力P2P → 推送 → 4K弹幕 → AList）， 缺类的垫最后。常用功能不用翻。
依赖是关键：所有 type 3 站都靠顶层 spider 指向的 jar 提供内置类。 一开始编排配置里**根本没有 spider 字段** → 所有特殊功能站都跑不起来。 现在用 cur/spider_special.jar（25.47 MB，自建 multi-dex， 覆盖 241/273 个内置类 = 92% 的 type3 站可跑）， 并写进 combo.json 的 spider 字段（相对路径，jar 必须与 json 同级）。
缺类的 14 个站仍然保留（分组标为「特殊功能·需补类」）， 不因为缺类就删 —— 要不要留由你决定。
